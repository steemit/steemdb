# SteemDB同步系统重构方案

## 项目概述
将现有的三个Python同步服务(history、sync、witnesses)整合为单一的Go同步服务，重点优化可靠性和吞吐量。保持MongoDB作为主数据库，Redis作为缓存层。

## 系统架构设计

### 整体架构
```
SteemDB同步系统 (Go)
├── 区块同步模块 (Block Sync)
├── 历史数据模块 (History)  
├── 见证人监控模块 (Witnesses)
├── 数据处理引擎 (Operation Processor)
├── 任务调度器 (Scheduler)
└── 监控告警模块 (Monitoring)
```

### 核心设计原则
- **单一服务**: 所有同步功能集成在一个Go进程中
- **模块化**: 内部按功能模块划分，便于维护
- **可靠性优先**: 完善的错误处理和恢复机制
- **高吞吐量**: 并发处理和批量操作优化

## 功能模块整合

### 1. 区块同步模块 (替代sync.py)
**核心功能**:
- 实时同步区块链数据
- 处理15种操作类型
- 批量处理优化(50个区块/批次)
- 操作队列管理

**性能目标**:
- 处理速度: 200-500 blocks/second
- 操作处理: 2000-5000 ops/second
- 错误恢复: <3秒自动重试

### 2. 历史数据模块 (替代history.py)
**核心功能**:
- 定期扫描所有账户(6小时周期)
- 批量获取账户详情(50账户/批次)
- 生成账户历史快照
- 统计数据更新

### 3. 见证人监控模块 (替代witnesses.py)
**核心功能**:
- 监控见证人状态(1分钟周期)
- 记录见证人错过区块
- 生成见证人历史快照
- 见证人投票统计

## 数据库架构分析

### 推荐方案: 保持MongoDB + 优化
**理由**:
1. **数据特性匹配**: 区块链数据天然适合文档存储
2. **零迁移成本**: 避免复杂的数据迁移过程
3. **性能已验证**: 现有MongoDB聚合查询性能良好
4. **团队熟悉度**: 减少学习和运维成本
